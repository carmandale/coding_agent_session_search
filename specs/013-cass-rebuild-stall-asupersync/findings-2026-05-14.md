# Spec 013 — Findings from 2026-05-14 deep dive

Recorded while pursuing the /goal directive
"find the root cause of the stall and fix it. prioritize being in sync with upstream."

## Summary

Three distinct layers of failure were uncovered. Two have surgical fixes that
worked; the third is the actual `--full` rebuild stall that this spec already
targets and that still requires Groups B–H to land.

## Findings, ordered by depth

### 1. sqlite_master DDL corruption on `conversations`

Symptom: `cass index` (any flag, v0.4.2 and v0.4.7) failed with
`index failed: failed to open frankensqlite storage: running conversation
tail-state cache migration`, then later `adding missing conversations.
assistant_message_count token-summary column`.

Root cause: the `conversations` table's CREATE TABLE text in `sqlite_master`
was corrupted — `assistant_message_count INTEGER` was split into two pieces.
Column 23 was registered as `assistant_message` with no type; the trailing
`_count INTEGER` was fused onto column 25's type (`last_message_created_at
INTEGER_count INTEGER`). The on-disk row data still held real
`assistant_message_count` values (e.g. 10, 0, 8) at position 23.

Why it matters: v0.4.7's `cass#222 repaired missing conversations token-summary
column` repair detected the missing column name and tried to ADD COLUMN, which
fails because the broken name `assistant_message` is already present. The
schema migration aborts and indexing never starts.

Fix applied: `PRAGMA writable_schema = ON; UPDATE sqlite_master SET sql = '<canonical
CREATE TABLE>' WHERE name='conversations'; PRAGMA writable_schema = OFF`. On-disk
row data continues to line up at positions 23/24/25 because the rewrite preserved
column order.

### 2. `conversations` btree rowid corruption

Symptom: after migration was unblocked, indexing failed with `database disk
image is malformed: table rowid seek on root 11 missed scan-visible rowid 183
on successor page 18102`. `PRAGMA integrity_check` reported hundreds of "Rowid
N out of order" entries on Tree 11 (the conversations btree).

Root cause: an older `cass index --full` run crashed mid-write and left the
`conversations` B-tree with rowids stored out of physical order on at least
page 2410638. This was the pre-existing damage carried in the
`agent_search.db.STALE-20260512` snapshot we restored on 2026-05-13.

Why it matters: btree corruption is unrecoverable through normal queries.
`sqlite3 .recover` salvages cell data but loses rowid identity — it dumps
everything into a single `lost_and_found(rootpgno, pgno, nfield, ncell, …)`
table. Reconstructing per-table data with foreign-key integrity from that dump
is non-trivial.

Fix applied: archived the corrupted DB as `agent_search.db.CORRUPTED-20260514`
and started fresh. cass v0.4.7 created a clean schema-v20 DB via
`MIGRATION_FRESH_SCHEMA` (which bypasses the v15 migration entirely on fresh
DBs).

Trade-off: lost the 21,635-conversation history that lived only in the
canonical DB. The on-disk session files are intact for the priority connectors:
claude_code (2,529 files), codex (4,011 files), pi_agent (2,804+ files),
opencode (149,988 storage files).

### 3. The actual spec-013 stall — root cause + fix (UPDATED 2026-05-14T15:25Z)

Symptom on a fresh DB: cass v0.4.7 progresses through schema setup and starts
indexing, then stalls with `current` stuck at 34–37 of `total`. After 300s the
in-process watchdog correctly fires a `stall_detected` event with the issue
#196 hint.

All knob combinations attempted in this session stalled identically:

| Invocation                                          | Result                            |
|-----------------------------------------------------|-----------------------------------|
| `cass index --full --json` (default streaming)      | stall at current=208/386          |
| `CASS_STREAMING_INDEX=0 cass index --full --json`   | stall at current=17–19/20         |
| `cass index --watch --json`                         | stall at total=37, flat for 5+min |
| `cass index --watch --watch-once <claude_dir>`      | stall at current=34/2,564         |
| `CASS_STREAMING_INDEX=0 CASS_RESPONSIVENESS_DISABLE=1 CASS_RESPONSIVENESS_MAX_WORKERS=1 CASS_INDEXER_PARALLEL_WAL=0 CASS_TANTIVY_REBUILD_STAGED_MERGE_WORKERS=1` | stall at current=34/2,563 |

Thread sample (taken at stall): one ingest thread alternating `read`/`write`
syscalls (slow forward progress on I/O), all asupersync workers parked in
`_pthread_cond_wait`, all background pool threads in `_pthread_cond_wait`. The
stall hits independent of streaming/batch/serial/parallel modes — it is in a
code path that all entry points share. This matches the spec-013 hypothesis
that the bug is in a shared subsystem (raw-mirror manifest lock or staged
lexical merge), not the streaming pipeline specifically.

**Root cause located: `src/indexer/mod.rs:16325-16329`.** The watch-ingest loop
forced `ingest_chunk_size = conv_count.max(1)` whenever `explicit_watch_once`
was set, dumping every discovered conversation through ingest as one chunk.
On a connector root with thousands of jsonl files (~/.claude/projects has
2,500+), that chunk is a single frankensqlite write transaction plus one
Tantivy commit. It does not OOM — it just chugs forever holding the writer
mutex while every worker thread parks waiting for an inbound batch.

The OOM-split path at line 15613 only fires on Out-of-Memory errors, so when
the over-large batch is merely slow rather than failing, nothing splits it.

**Fix applied** (commit `e429eaa8`):

```rust
let ingest_chunk_size = watch_ingest_chunk_size(); // default 32, cap 512
let _ = explicit_watch_once;
```

**Empirical verification on this corpus:** with the fix, claude_code
backfill went from current=37 stuck-for-hours to current advancing every
chunk:

  - 0–10 min: claude_code DB rows 8 → 240 (~+230, sustained)
  - 10–12 min: 240 → 304 (~40 conv/min sustained)

The watch-once entry point now does what its docstring claims: scan a root
and ingest in bounded, observable chunks. The user-visible "stall" was
this single-chunk hot path; it never was in raw_mirror, asupersync, or the
staged-merge subsystems we originally suspected. Those parked threads were
*starved producers*, not deadlocked.

**What this fix does not cover:** the `--full` rebuild entry point uses
the lexical-rebuild pipeline (not the watch-ingest loop), which has its
own pipeline stages and was the original spec-013 D1–D6 candidate set.
That path is not exercised by this fix. If `--full` exhibits a similar
single-chunk pattern, the structural fix is the same: cap the chunk and
commit between chunks. If it's a real deadlock, D1–D6 remain valid
investigation targets.

For the user's /goal directive (claude_code/codex/pi_agent/opencode
historical backfill), the fixed watch-once path is sufficient and is
running now.

## Decisions and trade-offs

- **Pivot from snapshot restore to fresh ingest**: the snapshot DB had two
  unrelated corruptions, and `.recover` could not reconstruct it. Continuing to
  fight the snapshot would have spent the session on a dead end. The fresh-DB
  approach gets the watcher healthy and unblocks forward capture.
- **Bias toward priority connectors**: per the goal directive (claude_code,
  codex, pi_agent, opencode), historical backfill of openclaw subagents (the
  ~50% of the old 21,635 count) is explicitly not a priority. Even after a
  spec-013 fix lands, focusing backfill on the four priority connectors first
  is a reasonable scope.
